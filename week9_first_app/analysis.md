# DailyTodo — 9주차 분석 기록

## 1. 분석 목적

7주차에 정한 개인 앱 아이디어인 DailyTodo를 바탕으로 사용자 문제, 후보 범위, 유사한 앱의 일반적인 기능 구조, 데이터·저장 방식, 위험과 수용 조건을 다시 점검한다. 본 문서는 7주차 제안서를 그대로 복사한 것이 아니라 10주차 구현을 시작할 수 있도록 범위와 판단 근거를 정리한 기록이다.

## 2. 후보 비교 및 선택

| 후보 | 해결하려는 문제 | 구현 범위의 예상 | 판단 |
|---|---|---|---|
| DailyTodo | 오늘 할 일과 완료 여부가 흩어져 확인하기 어려움 | 제목 입력, 목록, 완료 전환 | 핵심 행동이 단순하고 AC로 확인하기 쉬워 선택 |
| StudyGoal | 공부 목표와 달성 상태를 관리하기 어려움 | 목표 등록, 목록, 달성 상태 | 학습 목적에 더 집중하지만 이번 앱의 범위를 공부로 한정할 필요가 있음 |
| Habit Tracker | 반복 습관의 실천 여부를 꾸준히 기록하기 어려움 | 습관 등록, 날짜별 기록, 반복 처리 | 날짜와 반복 규칙이 필요해 첫 버전의 범위가 커질 수 있음 |

**선택:** DailyTodo

**선택 이유:** 하루의 할 일을 추가하고 완료 여부를 확인하는 최소 흐름에 집중할 수 있다. 반복 일정이나 날짜별 기록 없이도 첫 버전의 가치를 확인할 수 있어 10주차 첫 구현 범위로 적절하다.

※ 후보 비교는 주제 범위를 정리하기 위한 기획 판단이다. 교수님이 이 후보 비교를 승인했다는 뜻은 아니다.

## 3. 문제 분석

- **사용자:** 오늘 해야 할 일을 정리하려는 학생
- **상황:** 해야 할 일이 메모나 여러 곳에 흩어져 있다.
- **불편:** 오늘 할 일과 끝낸 일을 한눈에 구분하기 어렵다.
- **필요한 결과:** 한 화면에서 할 일을 추가하고, 목록을 확인하고, 완료 상태를 바꿀 수 있어야 한다.
- **최소 해결 흐름:** 입력 → 추가 → 목록 확인 → 완료 전환

이 문제를 해결하는 데 필요한 핵심 데이터는 할 일의 식별자, 제목, 완료 여부다. 우선순위나 통계, 알림은 첫 흐름을 성립시키는 데 필수적이지 않아 제외한다.

## 4. 유사 앱 및 기능 패턴 조사

할 일 관리 앱에서 흔히 볼 수 있는 기능 패턴을 기준으로 비교했다. 특정 앱의 최신 버전을 직접 설치·실행하거나 공식 기능 목록을 검증한 조사는 아니므로, 아래 내용은 기능 유형에 대한 기획 단계의 비교이며 특정 서비스의 확정 사양으로 인용하지 않는다.

| 기능 패턴 | 사용자에게 주는 가치 | DailyTodo 반영 |
|---|---|---|
| 할 일 입력 및 목록 | 해야 할 일을 한곳에서 확인 | 필수 |
| 완료 체크 | 끝낸 일과 남은 일 구분 | 필수 |
| 마감일·알림 | 일정 누락 방지 | 이번 버전 제외 |
| 반복·카테고리 | 여러 종류의 작업을 체계적으로 관리 | 이번 버전 제외 |
| 계정·동기화 | 여러 기기에서 목록 공유 | 이번 버전 제외 |

**조사 후 판단:** 첫 버전에서는 입력·목록·완료 체크만 구현한다. 일정·알림·동기화 기능은 핵심 흐름이 안정된 뒤 별도 범위로 검토한다.

## 5. 범위 조정 및 판단 근거

### 포함

- 제목 입력 및 추가
- 빈 제목 검증
- 목록 표시
- 항목별 완료/미완료 전환
- 빈 목록 안내

### 제외

- 로그인과 계정 관리
- 서버 및 클라우드 동기화
- 푸시 알림과 반복 일정
- 카테고리·태그·우선순위·통계
- 앱 재실행 후 영구 저장

### 저장 방식 결정

첫 구현은 앱 실행 중 메모리 목록으로 제한한다. 이 결정에 따라 AC는 앱을 재실행한 뒤에도 데이터가 남는다고 요구하지 않는다. 영구 저장이 필요해지면 별도 기능으로 범위를 다시 정하고 저장 방식과 AC를 함께 수정한다.

## 6. 데이터 흐름

| 데이터 | 의미 | 사용 위치 |
|---|---|---|
| `id` | 항목을 구분하는 고유 식별자 | 완료 상태를 바꿀 항목 선택 |
| `title` | 사용자가 입력한 할 일 제목 | 목록에 표시 |
| `isDone` | 완료 여부(true/false) | 체크 표시 및 상태 구분 |

흐름은 `입력값 검증 → 항목 생성 → 메모리 목록 추가 → 화면 갱신 → 완료 상태 변경`으로 정리한다.

## 7. 위험과 미확인 사항

| 항목 | 위험 또는 미확인 사항 | 대응 |
|---|---|---|
| 데이터 유실 | 앱 종료 시 메모리 목록이 사라짐 | 이번 버전의 제한으로 명시 |
| 빈 입력 | 공백만 있는 제목이 등록될 수 있음 | 앞뒤 공백 처리 후 빈 값 검증 |
| 중복 동작 | 추가 버튼을 여러 번 누르면 중복 등록될 수 있음 | 버튼 입력과 목록 추가 동작을 확인 |
| 잘못된 상태 변경 | 한 항목을 눌렀는데 다른 항목도 바뀔 수 있음 | `id` 기준으로 선택 항목만 갱신 |
| 제목 길이 | 최대 길이 기준 미정 | 수업 중 확인하거나 구현 전 결정 |
| 교수님 확인 | 주제·범위에 대한 확인 결과 미제공 | 다음 수업에서 확인하고 결과 기록 |

## 8. 앱 수용 조건과 검증 계획

| ID | Given | When | Then | 확인 증거 |
|---|---|---|---|---|
| AC1 | 앱의 할 일 목록 화면이 열려 있다. | `과제하기`를 입력하고 추가를 한 번 누른다. | 목록에 해당 제목이 한 개 나타난다. | 실행 화면 캡처 |
| AC2 | 입력란이 비어 있다. | 추가 버튼을 누른다. | 새 항목이 생기지 않고 입력 안내가 표시된다. | 실행 화면 캡처 |
| AC3 | 미완료 항목이 두 개 이상 있다. | 첫 번째 항목의 완료 표시를 누른다. | 첫 번째 항목만 완료 상태로 바뀐다. | 전후 화면 캡처 |
| AC4 | 목록에 항목이 하나도 없다. | 첫 화면을 연다. | 빈 목록 안내가 표시된다. | 첫 화면 캡처 |
| AC5 | 완료된 항목이 하나 있다. | 해당 항목의 완료 표시를 다시 누른다. | 해당 항목이 미완료 상태로 돌아간다. | 전후 화면 캡처 |

- **현재 검증 상태:** 미실행
- **검증 원칙:** 코드 작성 후 실제 앱을 실행해 각 행동과 결과를 확인한다. `flutter analyze` 성공만으로 화면 동작 AC가 통과했다고 판단하지 않는다.
- **증거 파일명 계획:** `week09/evidence/AC1_add.png`, `AC2_empty_input.png`, `AC3_toggle.png`, `AC4_empty_list.png`, `AC5_undo.png`

## 10. 10주차 구현 인계

**첫 작업:** DailyTodo 첫 화면에 입력란과 추가 버튼을 배치하고 AC1·AC2를 구현한다.

1. 개인 Flutter 개발환경과 저장소 접근 여부 확인
2. 첫 화면 기본 레이아웃 작성
3. `id`, `title`, `isDone` 데이터 구조 준비
4. 정상 제목 추가 및 빈 제목 거절 구현
5. 앱 실행 후 AC1·AC2 확인
6. 이후 목록 표시, 완료 전환, 빈 목록 안내 구현

- **GitHub 개인 저장소:** https://github.com/chlwoqls/flotter
- **현재 코드 위치:** DailyTodo 구현 코드의 실제 경로는 아직 확인되지 않음
- **실행 방법:** Flutter 프로젝트 폴더에서 `flutter run`
- **남은 기술 질문:** 제목 최대 길이, 공백 처리 기준, 상태 관리 방식
- **계정 개설·결제·배포:** 이번 과제 범위에 포함하지 않음
